## 🟡 Итерация 69 — Сброс данных: вход «первым пользователем»

Обнуляем пользовательские данные, чтобы пройти путь с нуля: первый вход → онбординг → создание команды → наполнение. Схема, миграции и справочник площадок остаются.

**Что важно знать перед сбросом:**

- `venues` **не трогаем.** CRUD площадок в приложении нет (только `GET /api/venues`), а `venue_id` обязателен при создании события — без площадки новый пользователь не создаст ни одного события. Остаётся единственная запись «Большая арена» (1000 ₽ с игрока / 10 000 ₽ аренда) вместе с её фото в Storage.
- Сброс обратим: перед очисткой все таблицы копируются в отдельную схему внутри той же БД. Схема не входит в `public`, поэтому через API не видна.
- Файлы в Storage через SQL удалить нельзя (триггер `protect_objects_delete`) — только через Storage API. Осиротевшие файлы ничему не мешают.

**Шаги:**

- ✅ 69.1 Бэкап: схема `backup_20260917`, в ней копии всех 18 таблиц `public` (`create table … as select *`). Количество строк сверено с `public` по каждой таблице; у ролей `anon` / `authenticated` / `service_role` доступа к схеме нет.
- ✅ 69.2 (2026-09-17, вариант «полный сброс» подтверждён пользователем) Очистка одной командой `TRUNCATE` 17 таблиц: `users`, `teams`, `team_memberships`, `team_invites`, `team_join_requests`, `team_default_lines`, `team_default_sides`, `team_section_images`, `events`, `event_attendances`, `event_lineups`, `event_lines`, `event_penalties`, `result_points`, `result_point_links`, `finance_transactions`, `media_items`.
- ✅ 69.3 Проверка: во всех 17 таблицах 0 строк, в `venues` — 1, миграций 32, бакет `team-media` на месте (34 файла).
- ✅ 69.3a Фикс перед первым входом: активная команда хранится в `localStorage` (`sh:active-team`) и уходит на сервер заголовком `X-Team-Id`, а менялась только ручным переключением в профиле. После сброса на устройстве остаётся id удалённой команды → `requireOrganizer` отвечает 403 на любую мутацию организатора, и переключателем в профиле это не лечится (он игнорирует выбор «текущей» команды). [src/app/(tabs)/layout.tsx](<../../src/app/(tabs)/layout.tsx>) теперь до рендера экранов приводит сохранённое значение к реальному членству. Тот же баг ловил бы любого, кто вышел из команды или был удалён из неё. **Нужен деплой до первого входа.**
- 69.4 Первый вход пользователя: `requireUser` создаёт строку `users` с `onboarded = false` → `/onboarding` → создание команды → роль organizer. Пользователь проходит путь руками и фиксирует, что мешает.
- 69.5 Storage: 33 осиротевших файла (~56 МБ: медиа, аватары, лого, картинки разделов) — удалить через Storage API, когда будет локальный `.env.local`; папку `venues/` оставить. Не блокирует.
- 69.6 Удалить схему `backup_20260917`, когда новая команда обживётся и откат точно не понадобится.

## Развилка — направление версии

Решаем после 69.4. Детализация до итераций — когда выберем.

### Вариант A — Одна команда

Заводим одну реальную команду, добавляем ребят и концентрируемся на её живом использовании. Пул задач наполняется из того, что мешает этой команде.

### Вариант B — Привязка к Telegram-каналу

Привязываем бота к конкретному каналу в Telegram. Пересекается с эпиком «Бот в групповом чате команды» из [v0.7](v0.7.md) (`/connectchat`, посты о событиях с inline-голосованием, дайджесты) — при выборе B переносим нужные пункты оттуда. Эпик: [features/notifications.md](../features/notifications.md).
