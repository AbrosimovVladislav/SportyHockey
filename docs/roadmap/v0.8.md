## 🟡 Итерация 70 — Анонсы в чат команды (группа или канал Telegram)

Бот публикует анонс события в канал команды: фото + текст + кнопка «Записаться». Кнопка открывает Mini App сразу на странице события; новичок по дороге автоматически вступает в команду и разрешает боту писать в личку.

**Как устроена связка (сверено с документацией Telegram Bot API и Mini Apps):**

- Mini App привязана к **боту**, не к каналу. К каналу привязывается только бот: его добавляют администратором с правом «Публикация сообщений» (`can_post_messages`), и его посты выглядят как посты самого канала.
- Кнопки типа `web_app` работают **только в личке с ботом** — в канале Telegram их не принимает. Поэтому в анонсе обычная url-кнопка со ссылкой на Main Mini App бота: `https://t.me/<bot>?startapp=<параметр>`. Параметр приходит в приложение как `start_param` / `tgWebAppStartParam`.
- Кто открыл Mini App по ссылке и ни разу не писал боту, личных сообщений от бота не получит. Лечится нативным запросом `requestWriteAccess` (Bot API 6.9+); признак «уже разрешил» — `allows_write_to_pm` в `initData`.
- Сейчас переход на событие из бота **не работает**: клиент понимает только `join_<token>`, а `event_<id>` открывает главную. Чиним в этой же итерации.

**Решения пользователя:** новичок из канала вступает в команду автоматически (кнопка несёт invite-токен); личные сообщения о новом событии остаются вместе с постом в канал; картинка анонса — готовое фото, а не генерируемый постер; публикация — при создании события (переключатель) и вручную кнопкой.

**Что нужно от пользователя до теста:** (1) у бота в @BotFather настроена Main Mini App — проверка: ссылка `https://t.me/<bot>?startapp=test` открывает приложение; (2) бот добавлен в группу команды (см. 70.8; для канала — администратором с правом публикации).

### ✅ 70.8 — Группа вместо канала (2026-09-17)

После первого деплоя выяснилось: у команды не канал, а **группа**. Публикация, кнопка «Записаться», авто-вступление, запрос на личку и реплаи от типа чата не зависят (хранится просто `chat_id`) — переделана только привязка, плюс три особенности групп. Сверено с документацией Telegram (Bot Features → Privacy Mode, Bot API → Message).

- **Привязка группы.** Пересланное из группы сообщение id чата не несёт, поэтому способ канала не годится. Вместо этого: (1) бота добавляют в группу — служебное сообщение `new_chat_members` бот получает всегда, даже в privacy mode; если добавил админ группы, управляющий командой, чат привязывается сразу; (2) запасной путь и перепривязка — команда `/connect@<бот>` в группе (адресованные боту команды доходят и в privacy mode). Webhook перенастраивать не нужно: это обычные `message`.
- **Страховка от случайного переноса.** Авто-привязка при добавлении срабатывает только для команды без привязанного чата; перенос анонсов в другую группу — только явным `/connect`.
- **Права.** Боту в группе достаточно быть участником, которому не запретили писать (админом — надёжнее: ограничения группы на медиа его не касаются). Привязывающий обязан быть админом группы и организатором в приложении; «анонимный админ» получает просьбу написать не анонимно.
- **Темы.** Миграция `teams_announce_thread` → `teams.announce_thread_id`: `/connect`, отправленный в теме форум-группы, направляет анонсы в эту тему.
- **Смена id чата.** При превращении группы в супергруппу Telegram меняет id: обрабатываем служебное `migrate_to_chat_id` (команда и уже опубликованные анонсы), а при публикации — ошибку с новым id (запоминаем и повторяем один раз).
- **UI.** Формулировки нейтральные: «Чат анонсов», «Анонс в чат команды», «Анонсировать в чат»; инструкция в настройках — под группу, канал — примечанием.

### Как это работает, когда команд много

Продумано 2026-09-17, схема уже так и реализована:

- **Один бот на все команды, у каждой команды — свой канал.** Привязка хранится в `teams.announce_chat_id`; бот может быть администратором в любом числе каналов. Анонс уходит в канал той команды, которой принадлежит событие. Перепривязка просто заменяет канал.
- **Одна Mini App на всех.** Кнопка «Записаться» несёт id события и invite-токен именно этой команды — человек попадает в нужную команду и на нужное событие, активная команда в приложении переключается сама.
- **Защита от чужих каналов.** Бот общий, поэтому при привязке проверяются обе стороны: отправитель управляет командой в приложении **и** является администратором самого канала. Иначе любой мог бы переслать пост из чужого канала, где бот уже админ, и слать туда свои анонсы.
- **Человек в нескольких командах.** Личная карточка события от бота показывает название команды; при привязке канала бот спрашивает, к какой из команд его привязать.
- **Часовые пояса.** Сервер живёт в UTC, команды могут быть в разных городах — время в сообщениях бота пишется в поясе команды (`teams.timezone`, берётся с устройства организатора автоматически).
- **Один канал на две команды** (клуб с двумя составами) технически возможен — ограничения нет, анонсы обеих команд пойдут в общий канал.
- **Группа или канал — на выбор команды:** у одних группа с обсуждением, у других канал только для объявлений; поддержаны оба, привязка отличается (см. 70.2 и 70.8).
- **Чего пока нет:** очередь отправки — Telegram ограничивает бота ~30 сообщениями в секунду, на сотнях команд личную рассылку придётся ставить в очередь; бот не узнаёт сам, что его убрали из чата (webhook не получает `my_chat_member`) — ошибка всплывёт при следующей публикации понятным текстом.

Инструкции про `/connect` и канал из интерфейса убраны (сами механизмы работают как запасные). Общая проверка прав вынесена в [src/lib/announce-chat.ts](../../src/lib/announce-chat.ts).

## Итерация 73 — Роли: админ / организатор / игрок

Сейчас ролей две: `organizer` и `player`. Добавляем над ними `admin` — один на команду, создатель. **Решение пользователя:** организатор умеет всё, что умеет сейчас; только админ назначает и снимает организаторов, архивирует команду и привязывает группу. Начинаем после того, как пользователь пройдёт проверку 70–72.

### 73.1 — Схема БД

Миграция `team_memberships_admin_role`: CHECK роли → `admin / organizer / player`; частичный уникальный индекс «не больше одного админа на команду»; бэкфил — в каждой команде без админа самый ранний организатор становится админом (в «Wolves» это пользователь).

### 73.2 — Сервер

- [src/lib/role.ts](../../src/lib/role.ts): `MemberRole` с `admin`, хелпер «управляющая роль» (admin или organizer), `asMemberRole` понимает `admin`.
- [src/lib/auth.ts](../../src/lib/auth.ts): `requireOrganizer` пропускает админа и организатора — все существующие организаторские роуты работают для админа без правок; новый `requireAdmin`.
- `POST /api/teams`: создатель команды получает `admin`.
- `PATCH /api/teams/me/members/[user_id]`: менять роль может только админ; роль самого админа не меняется. `DELETE`: админа удалить нельзя; организатора удаляет только админ.
- `POST /api/teams/me/archive` и привязка / отвязка канала — только админ. `POST /api/teams/me/leave`: админ выйти не может (передача админства — в кандидатах).
- Проход по ~16 серверным файлам с литералом `'organizer'`: получатели заявки об оплате, проверки в заявках на вступление, удалении медиа и финансах — везде «управляющая роль» через хелпер.

### 73.3 — Клиент

- `useIsOrganizer` возвращает `true` и для админа (29 файлов с проверкой роли не трогаем); новый `useIsAdmin`.
- Редактирование игрока: выбор роли «Игрок / Организатор» виден только админу. Вкладка «Роли» и профиль: три ярлыка — «Админ», «Организатор», «Игрок». «Опасная зона» (архив) и отвязка канала — только у админа.
- i18n: ключи ролей.

### 73.4 — Build check и документация

`pnpm typecheck && pnpm build`; [features/team.md](../features/team.md), [ARCHITECTURE.md](../ARCHITECTURE.md) (поток авторизации), `src/types/db.ts`.

### Шаги тестирования 73

1. Профиль и вкладка «Роли»: у пользователя ярлык «Админ».
2. Открыть игрока → редактирование → назначить организатором → у него появились раздел «Деньги», создание событий, настройки команды.
3. Зайти этим организатором: в редактировании игроков **нет** выбора роли; нет архива команды и отвязки канала; удалить другого организатора нельзя.
4. Организатор создаёт событие, отмечает явку и оплату — работает как раньше.
5. Админ снимает роль организатора → человек снова игрок, организаторские разделы пропали.
6. Попытки удалить админа или сменить ему роль, выход админа из команды — понятный отказ.
7. Новый аккаунт создаёт свою команду → он в ней админ.
8. Игрок отправляет «Я оплатил» → уведомление получают и админ, и организаторы.
