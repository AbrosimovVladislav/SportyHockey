## ✅ Итерация 29 — Создание игрока и приглашение

Эпик: [features/team.md](../features/team.md) · [features/onboarding.md](../features/onboarding.md)

Два пути попадания игрока в команду. И приглашение (организатор позвал), и заявка (игрок попросился сам) — это одна сущность «ожидающая связь игрок↔команда», различается только направлением (`kind`). В команду никто не попадает без подтверждения второй стороны.

**Flow 1 (игрок пришёл сам):** по ссылке проходит онбординг (видим его Telegram-аккаунт), заполняет свой профиль и выбирает одну команду → отправляет заявку → ждёт аппрува организатора.

**Flow 2 (организатор завёл игрока):** заводит карточку игрока заранее (игрок без аккаунта — числовой `telegram_id` NULL; username при этом организатор может вписать руками). Если включён свитчер «Пригласить в приложение» — получает invite-ссылку и сам пересылает её игроку. Игрок переходит, видит ту же форму онбординга уже предзаполненной своими данными, правит при желании — и сразу в команде.

Создание игрока, редактирование публичного профиля (28.5) и онбординг — это, по сути, одна форма с теми же полями; визуально могут отличаться.

**БД (минимум)**

- ✅ 29.1 Одна таблица `team_join_requests` — и приглашения, и заявки: `id, team_id, user_id, kind ('invite' | 'request'), status ('pending' | 'approved' | 'rejected'), created_by, created_at, decided_by, decided_at`. FK на teams/users `on delete cascade`. Отдельного токена нет — invite-ссылка несёт `user_id` игрока без аккаунта (UUID сам по себе непредсказуем).
- ✅ 29.2 `users.onboarded` (boolean, default false) — прошёл ли человек онбординг (заполнил свой профиль). Нужно для роутинга: членство есть, но `onboarded = false` (приглашённый, ещё не открывал онбординг) → ведём на онбординг, иначе домой.
- Новых контактных полей не заводим: Telegram-ник — существующий `users.username` (делаем редактируемым), WhatsApp — существующий `team_memberships.contact_phone` (`wa.me` строится из него).

**Единая форма профиля**

- ✅ 29.3 Форма данных игрока `MemberForm` (имя, фамилия, дата рождения, амплуа, номер, позиция, хват, телефон, Telegram-ник, фото) — один компонент на три экрана: создание игрока, редактирование профиля (28.5), онбординг. Без клонирования.
- ✅ 29.4 Telegram-ник в форме пишет/читает `users.username`. Кружок Telegram в профиле (`header-card.tsx`) уже строится из `username` — менять нечего; WhatsApp из телефона, как сейчас.
- ✅ 29.5 Новый примитив `Switch` (свитчер) в `src/components/`.

**Flow 2 — организатор заводит игрока**

- ✅ 29.6 Зелёная кнопка (`FAB`) в `/squad` (24.1) открывает экран создания игрока `/squad/new` вместо заглушки «скоро».
- ✅ 29.7 На экране — `MemberForm` + свитчер «Пригласить в приложение». Выключен → просто заводим игрока без аккаунта; включён → плюс генерим приглашение.
- ✅ 29.8 API `POST /api/teams/me/members` (organizer). Ника ещё нет в системе → создаём `users` (telegram_id NULL, username из формы, onboarded=false) + `team_memberships` (player). Ник уже есть → дубль не плодим: привязываем существующего игрока к команде новым `team_memberships`, его личный профиль не трогаем (только командные поля). Уже в этой команде → 409 «Этот игрок уже в твоей команде». Приглашение (`team_join_requests` kind='invite') — только при включённом свитчере и если у игрока ещё нет аккаунта (telegram_id NULL).
- ✅ 29.9 При включённом свитчере после «Создать» — bottom sheet со ссылкой (`?start=invite_{userId}`) и тремя действиями: «Отправить приглашение» (нативный Telegram-шит «Поделиться», `shareURL`), «Скопировать», «Готово» → назад на состав. Свитчер выключен — просто создаём и возвращаемся. Хук `useCreateMember`; список состава форсированно рефетчится (`refetchType: 'all'`), чтобы новый игрок был виден сразу.
- ✅ 29.10 Бот: `?start=invite_{userId}` → по `userId` находит карточку игрока без аккаунта и привязывает реальный Telegram перешедшего (telegram_id/username, заявку помечает accepted, защита от гонки `telegram_id IS NULL`). Краевые случаи обработаны сообщениями: повторный переход тем же человеком → «Готово»; перешедший уже имеет аккаунт → «попроси организатора добавить тебя в команду»; битая ссылка → «недействительна».
- ✅ 29.11 Приглашённый при входе попадает на онбординг с предзаполненными полями (его данные из карточки) → правит при желании → «Готово» ставит `onboarded=true`. Роутинг: членство есть + `onboarded=false` → онбординг.

**Flow 1 — игрок пришёл сам**

- ✅ 29.12 Шаг «Я игрок» в онбординге (заменяет заглушку `onboarding.player`): игрок заполняет свой профиль (`MemberForm`, Telegram-данные уже подставлены) и выбирает **одну** команду → отправляет заявку.
- ✅ 29.13 API `POST /api/me/onboard` (авторизованный): ставит `onboarded=true` и пишет профиль; при переданном `join_team_id` без членства — строка `team_join_requests` (kind='request', pending), без дублей по pending. Членство не создаёт.
- ✅ 29.14 Экран «Заявка отправлена — ждём подтверждения» (`WaitingStep`). Роутинг: членства нет + есть pending-заявка → этот экран.
- ✅ 29.15 Приём заявок организатором — минимально в `/profile` (`join-requests-card`): список pending-заявок с approve/reject. Approve → создаёт `team_memberships` (player) + закрывает заявку (игрок появляется в составе сразу). Reject → закрывает заявку без членства. Повторное решение → 409.

**Один Telegram-ник = один игрок**

- ✅ 29.16 Уникальность в `users`: `telegram_id` уникален; `username` уникален частичным индексом по `lower(username)` (регистронезависимо; пустой/NULL не ограничены). Совпадение ника при создании ищется регистронезависимо и с экранированием `_`. Дружелюбные 409 при занятом нике — и при создании, и при редактировании профиля.

## Итерация 33 — Применение дефолтной раскидки в событии

Эпик: [features/lineup.md](../features/lineup.md)

Дефолтные звенья (итерация 30) и распределение Светлые/Тёмные (итерация 31) задаются на уровне команды — здесь они начинают работать в стандартных кейсах создания события.

- При создании игры/события состав предзаполняется из `team_default_lines`.
- При создании тренировки распределение Светлые/Тёмные предзаполняется из `team_default_sides`.
- Кнопка «Сбросить к дефолту команды» в составе и в распределении события.
- Дефолт применяется к тем, кто идёт в событие; пришедшие сверх дефолта — в запас/пул.
