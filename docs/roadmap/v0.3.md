# v0.3 — Прочие секции раздела «Команда»

**Цель:** закрыть оставшиеся секции раздела «Команда» поверх готового «Состава» (v0.2): главная раздела (хаб), Статистика, Медиа, Настройки команды, Заявки.

Раздел «Команда» (4-й нижний таб, бывший «Состав») получает **главную страницу-хаб** по образцу страницы события `/events/[id]`: шапка, сводка по команде и список секций. Секции (Статистика / Медиа / Настройки / Заявки) дозаполняются по итерациям; до реализации каждая открывает заглушку «Скоро».

**Итерации:** 36, 37, 38, 39, 40, 41, 42 (сквозная нумерация; v0.2 закрылась на 35). Тактика, изначально запланированная как итерация 43, **вынесена в post-MVP** — направление наименее проработано, нужен отдельный брейншторм после релиза. В хабе раздела «Команда» пункт «Тактика» остаётся как замьюченная заглушка (см. итерацию 42, пункт 42.4).

Эпик: [features/stats.md](../features/stats.md)

Экран `/squad/stats` поверх готовой модели `result_points` (v0.2) и нового сохранённого исхода события. Под шапкой — два уровня переключателей: основные табы «Статистика / Аналитика» и под ними глобальные сегмент-чипы «Игры / Тренировки» (влияют на обе вкладки).

**База данных и пересчёт исхода события**

- ✅ 37.1 Миграция через Supabase MCP (`events_add_outcome`): добавлена колонка `events.outcome` (`text` с CHECK на `'win' | 'draw' | 'loss'`, nullable). Для тренировок и для игр без зафиксированного счёта — `NULL`. Типы перегенерированы (`src/types/db.ts`).
- ✅ 37.2 Хелпер `recomputeEventOutcome(sb, eventId)` в `src/lib/event-outcome.ts`: считает счёт по `result_points` (`type='goal'`, `team_side own/opponent`) и пишет результат в `events.outcome`. Подключён в `POST/PATCH/DELETE /api/events/[id]/goals[/goalId]`. Существующие игры на стенде один раз пересчитаны единым SQL.

**API и DTO**

## ✅ Итерация 40 — Финализация статуса событий в БД

Эпик: [features/events.md](../features/events.md)

До этой итерации поле `events.status` принимало в БД только два значения — `scheduled` и `cancelled`. Реальное «завершено или нет» вычислялось на лету в DTO через `effectiveEventStatus(raw, ends_at)` и в БД не записывалось. Из-за этого агрегаторы (статистика, финансы, бот) не могли фильтровать по «реально завершённым»: либо фильтр по `status='completed'` ничего не возвращал, либо использовался хрупкий обход через `starts_at <= NOW()`. Итерация делает БД единой точкой истины: статус всегда соответствует реальности, и все потребители просто читают его из колонки.

Подход — «ленивая финализация при чтении»: эндпоинты, которые и так возвращают события, дополнительно проверяют расхождение между хранимым статусом и реальным состоянием по `ends_at` и при необходимости отправляют точечный UPDATE по конкретным id. Никаких cron-задач, никаких pg_cron, никаких внешних очередей. Если расхождений нет — UPDATE не отправляется вообще, нагрузка нулевая.

- ✅ 40.1 Helper `src/lib/event-finalize.ts` — функция `finalizeRows(sb, rows)` с симметричной логикой: `scheduled + ends_at < now → completed` (событие прошло); `completed + ends_at >= now → scheduled` (организатор перенёс уже-завершённое событие на будущее через reschedule). События без `ends_at` и `cancelled` не трогаются. UPDATE отправляется одним SQL c `IN (ids)` только при наличии конкретных расхождений; возвращает тот же массив с подменённым `status` у затронутых строк.
- ✅ 40.2 Список событий `/api/events` GET: выборка прогоняется через `finalizeRows` до формирования DTO. Поле `status` в ответ кладётся напрямую из БД через `asEventStatus`, вычисление на лету (`effectiveEventStatus`) убрано.
- ✅ 40.3 Детальный эндпоинт `/api/events/[id]` GET: одно событие проходит через `finalizeRows([rawEvent])`. Точечный UPDATE по id отправляется только при расхождении статуса.
- ✅ 40.4 Командная статистика `/api/teams/me/stats`: SELECT забирает только события с `status='completed'` прямо в SQL — без `finalizeRows`. Статистика и аналитика принципиально работают по уже завершённым событиям, а «дозревание» статуса гарантированно отрабатывает на расписании (40.2) и в детальной карточке (40.3); ещё одна точка отказа на /squad/stats не нужна и UPDATE при заходе в статистику не отправляется. Прежний костыль с `starts_at <= NOW()` снят.
- ✅ 40.5 Удалена функция `effectiveEventStatus` из `src/lib/event-enum.ts` — единая точка истины теперь в БД, вычислять статус на лету больше не нужно. `asEventStatus` остаётся как нормализатор enum.
