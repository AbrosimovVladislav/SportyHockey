## Модель денег команды (один источник, разрезы по запросу)

Принципиальный момент: все деньги команды живут в одной таблице `finance_transactions` (`income / expense`-вселенная). Никаких отдельных «долгов», «депозитов», «возвратов» как отдельных сущностей — это вычисляемые разрезы поверх ленты транзакций. Что меняется относительно текущей схемы — добавляем `category` (для расходов) и `occurred_on` (фактическая дата операции для бэкдейта), плюс типы `deposit` и `adjustment` нормализуются.

**Семантика типов транзакции (`type`):**

- **`player_payment`** — игрок заплатил команде. Есть `user_id`, есть `event_id` (когда оплата привязана к конкретному событию) либо его нет (когда это депозит или обобщённая оплата).
- **`expense`** — команда потратила деньги наружу (аренда, инвентарь, форма, прочее). Без `user_id`. Категория — в `category`.
- **`refund`** — команда вернула деньги игроку (отказ от участия, переплата). Есть `user_id`, отрицательная сумма к балансу игрока. (Альтернатива — отдельная подкатегория `category='refund'` у `expense`; на реализации решим, что лучше — см. ниту в итерации 50.)
- **`adjustment`** — ручная корректировка баланса игрока организатором («простил долг», «бонус», «штраф»). Есть `user_id`, без `event_id`. Сумма со знаком.

**Долги / переплаты / депозиты — не записи, а агрегаты:**

- **Долг игрока** = ∑ `cost_per_player × showed_up` за прошедшие события − ∑ `player_payment + adjustment` (если итог положительный = игрок должен).
- **Переплата** = тот же расчёт, но итог отрицательный (команда должна игроку).
- **Депозит** = `player_payment` без `event_id` — игрок внёс деньги «вперёд», тратятся при следующих событиях. Технически — частный случай переплаты.

Логика уже работает в `src/lib/player-finance.ts`; перевозим её на новые типы и обогащаем `adjustment`-ом.

**Баланс команды (карточка на хабе):** не голый `income − expense`. Считаем разложение:

```
Баланс = На руках − Будущие аренды − Переплаты игроков + Долги игроков

На руках = ∑ player_payment − ∑ expense (на дату «сегодня»)
Будущие аренды = ∑ expense (category=arena) с occurred_on > today
Переплаты = ∑ положительных балансов всех игроков (где команда должна игроку)
Долги = ∑ отрицательных балансов всех игроков (где игрок должен команде)
```

Это и есть «честный» баланс — сколько денег у команды останется после закрытия всех обязательств и расходования всех уже запланированных трат.

## Каркас раздела «Деньги»

Пять экранов плюс три bottomsheet'а:

1. **Хаб `/money`** — баланс-карточка, 3 quick-actions (Оплата игрока / Депозит / Расход), меню из 4 пунктов в подэкраны, лента последних операций.
2. **Финансовый срез `/money/report`** — отчёт за период.
3. **Балансы игроков `/money/players`** — текущий срез по всем игрокам.
4. **Операции `/money/transactions`** — универсальный лог с фильтрами.
5. **Аналитика `/money/analytics`** — графики динамики и прогноз.

Bottomsheet'ы: оплата игрока, депозит, расход. Открываются из quick-actions и из подэкранов (например, на «Балансах игроков» по тапу на должника).

- [src/lib/player-finance.ts](../../src/lib/player-finance.ts) — расчёт `balance / total_charged / total_paid / rows` для одного игрока; расширим под `adjustment` и категории.

- `useActiveTeamStore` + `X-Team-Id` + `getUserTeamId` — мультикомандность уже работает end-to-end.

## Что нужно новое (специруем в итерациях)

- Миграция БД: `finance_transactions.category text NULL`, `finance_transactions.occurred_on date NOT NULL DEFAULT (created_at::date)`, CHECK на `type` (`player_payment / expense / refund / adjustment`) и на `category` (`arena / inventory / uniform / other` плюс `NULL` для не-расходов).
- API: `GET /api/finance` (лента с фильтрами), `POST /api/finance` (создание), `PATCH /api/finance/<id>`, `DELETE /api/finance/<id>` (правка/удаление организатором), `GET /api/finance/balance` (разбивка для хаба), `GET /api/finance/report` (агрегаты за период), `GET /api/finance/players` (балансы всех игроков команды), `GET /api/finance/analytics` (помесячные точки для графиков).
- UI: пять экранов и три bottomsheet'а. `PeriodPicker` — общий компонент выбора периода (текущий месяц / прошлый месяц / 3 месяца / всё время / кастом).

## ✅ Итерация 48 — Каркас БД и хаб `/money`

База: расширяем `finance_transactions`, переписываем экран хаба, ставим базовое API. После итерации работает баланс-карточка, лента последних операций и тап в подэкраны (заглушки).

- 48.1 Миграция `finance_transactions_categories_and_dates`: добавляет `category text NULL` с CHECK in (`'arena','inventory','uniform','other'`); добавляет `occurred_on date NOT NULL DEFAULT (created_at AT TIME ZONE 'UTC')::date` (backfill для существующих записей); добавляет CHECK на `type` (`'player_payment','expense','refund','adjustment'`) — мигрируем legacy-значения, если такие есть. Типы перегенерированы (`src/types/db.ts`).
- 48.2 `GET /api/finance/balance` (`requireUser` + активная команда): возвращает разбивку `{ on_hand, future_arenas, overpayments, debts, total }` за «сегодня». `on_hand` = ∑ `player_payment` − ∑ `expense` с `occurred_on ≤ today`. `future_arenas` = ∑ `expense` (category=arena) с `occurred_on > today`. Переплаты/долги — агрегатами через расширенный `computeTeamBalances` (см. 48.3).
- 48.3 `src/lib/team-finance.ts`: новый общий модуль. `computeTeamBalances(sb, teamId)` — массово считает балансы всех игроков команды одним проходом (выборка `attendance + finance_transactions` за всё время команды). Возвращает `{ players: [{ user_id, balance, total_charged, total_paid }] }`. Используется и в `/api/finance/balance`, и в `/api/finance/players`.
- 48.4 `GET /api/finance` (`requireUser` + активная команда): лента транзакций с пагинацией. Фильтры query-string: `from`, `to` (по `occurred_on`), `type`, `category`, `user_id`, `event_id`, `kind=income|expense`. Сортировка `occurred_on desc, created_at desc`. JOIN на `users` (имя/аватар) и `events` (название/дата). Дефолтный лимит — 50, курсор по `created_at`.
- 48.5 `POST /api/finance` (`requireOrganizer` + активная команда): создание транзакции. Тело — `{ type, amount, occurred_on, category?, user_id?, event_id?, description? }`. Валидация zod: type-specific (для `player_payment` — `user_id` обязателен; для `expense` — `category` обязателен; для `adjustment` — `user_id` обязателен; для `refund` — `user_id` обязателен). Сумма всегда положительная — знак на агрегатах вычисляется по `type`.
- 48.6 DTO в `src/types/api.ts`: `FinanceTransaction`, `FinanceListResponse`, `TeamBalanceResponse`, `CreateFinanceRequest`. Типы транзакции — литеральный union, не string.
- 48.7 Хуки: `useTeamBalance()`, `useFinanceList(filters)`, `useCreateFinance()` (мутация инвалидирует `['team-balance']`, `['finance']`, `['player-finance', user_id]`).
- 48.8 Экран `/money/page.tsx` переписывается с нуля:
  - Шапка `LightHeader` «Деньги», без кнопки back (страница верхнего уровня).
  - **Карточка баланса**: крупно итог со знаком (зелёный при ≥0, красный при <0), под ним 4 строки разбивки («На руках 100 000 ₽», «Будущие аренды −80 000 ₽», «Переплаты −16 000 ₽», «Долги +12 000 ₽»). Источник — `useTeamBalance`.

## ✅ Итерация 54 — Аналитика финансов `/money/analytics` и финальная полировка

Графики и прогноз. Берём `recharts` (или нативный canvas, если не хотим зависимости — решим на реализации). Прогноз — простой, на запланированные события вперёд.

- 54.1 `GET /api/finance/analytics?from&to` (`requireUser` + активная команда): возвращает массивы помесячных (или понедельных при коротком периоде) точек — `{ balance_over_time: [{ date, value }], collections_per_month: [{ month, value }], expenses_per_month_by_category: [{ month, arena, inventory, uniform, other }], debts_over_time: [{ date, value }], deposits_overpayments_over_time: [{ date, deposits, overpayments }] }`. Внутри — один запрос лент + развёртывание в массив дней (нарастающий баланс).
- 54.2 `GET /api/finance/forecast` (`requireUser` + активная команда): прогноз на 1/2/3 месяца вперёд. Алгоритм: на каждое будущее событие (`start_at > today, archived_at IS NULL`) ожидаемая явка = средняя явка за последние 6 событий того же типа (тренировка/игра), ожидаемый сбор = ожидаемая явка × `cost_per_player`. Запланированные `expense` с `occurred_on > today` — учитываются как есть. Возвращает `{ months: [{ month, expected_income, planned_expense, projected_balance }] }`.
- 54.3 Хуки `useFinanceAnalytics(period)`, `useFinanceForecast(horizon)`.
- 54.4 Экран `/money/analytics/page.tsx`:
  - `LightHeader` «Аналитика финансов», back на `/money`.
  - `PeriodPicker` сверху.
  - **График 1** — Динамика баланса (linear chart). Накопительная линия по `balance_over_time`. Горизонтальная нулевая ось.
  - **График 2** — Сборы по месяцам (bar chart). Один бар = один месяц.
  - **График 3** — Расходы по месяцам (stacked bar chart). Стэк по категориям с легендой.
  - **График 4** — Динамика долгов (linear chart).
  - **График 5** — Депозиты и переплаты (две линии).
  - **Блок «Прогноз»** в конце: сегментед-контрол «1 / 2 / 3 месяца», под ним строки по месяцам — ожидаемый сбор, запланированные траты, прогнозируемый баланс на конец месяца. Текстовое summary: «При текущей средней явке на следующие 3 месяца ожидается +24 000 ₽ ».
- 54.5 На `/money` пункт «Аналитика» подключается к этому экрану.
- 54.6 i18n `money.analytics.*`, `money.forecast.*`.
- 54.7 Доводка по фидбеку пилотов (резерв — точечные правки UX/тексты после обкатки трёх предыдущих итераций).
